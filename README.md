# 台北環衛模型（Taipei Environmental Health Model）

把台北市的環境衛生議題放上同一座立體台北：以開放資料推估風險熱區、以族群模型預估防治任務的效果、把任務與回報放在同一條時間軸上。
第一個落地的主題是**鼠類（溝鼠）**；其餘 21 個主題（登革熱病媒蚊、髒亂點、側溝淤積、空氣品質…）已列入主題選單，標示「待整合」。

> 熱區是依環境條件與模型推估的相對值，不是實際捕鼠數或通報數。預載的回報為模擬資料。

## 這個專案做了什麼

專案分三層，由下往上疊：

1. **資料地圖**（`dist/index.html`，deck.gl）
   從 data.taipei / data.gov.tw 下載污水與雨水下水道、攤販集中場、傳統市場、垃圾車停靠點、餐飲業者（47,031 家，本機地址比對定位）等資料，
   在建置階段把六項因子的密度烤成熱力貼圖，前端只做顯示與開關，縮放旋轉不重算。另有鳳頭蒼鷹紀錄、廚餘收受點等對照圖層，不進權重。
2. **立體台北模型**（`dist/model.html`，three.js）
   內政部 20 m DEM 做地形、Sentinel-2 衛星影像依都市計畫分區重新著色做頂面、沿市界切出泥土剖面與底座，光線對齊衛星拍攝時刻。
3. **防治管理工具**（同一頁，`dist/js/`）
   - **族群模型**：全市 26,841 個 100 m 網格，環境因子 → 承載量 K，族群 N 以 logistic 逐日朝 K 回升；任務扣族群或降承載量並把一部分外溢到外環；回報依距離與半衰期加成。從 90 天前推到未來 30 天。
   - **里**：456 里界、里分級著色、里資訊卡（等級、近期回報、進行中任務、上次／下次噴藥）。
   - **任務**：投藥、環境清消、捕鼠籠、填補鼠洞四種類型，含執行單位、配套措施、藥劑、經費、民眾通知、稽核紀錄；投藥任務自動檢查 1 km 內的鳳頭蒼鷹紀錄（二次中毒風險）；建立前可比較範圍內與外溢環帶的預估變化。
   - **定期噴藥**：預載環保局戶外環境噴藥日程（各區清潔隊月曆 PDF 解析，2,688 筆、456 里全覆蓋）。
   - **回報**：鼠種、跡證、信心度篩選，JSON 匯入驗證。
   - **設定**：每個參數標示文獻或「假設」，拉動即時重算。
   - **示範與導覽**：寧夏夜市情境（台上逐步、自動影片、臺北通推播示意）、12 步新手導覽。

## 快速開始

```bash
npm install
npm run fetch          # 下載原始資料到 raw/
npm run build          # 清洗、轉座標、烤熱力與管線貼圖 → dist/data/
npm run build:grid     # 100 m 因子網格＋里界（管理工具用）
npm run build:sim-reports   # 模擬回報
npm test               # 族群模型與匯入驗證（13 項）
npm run serve          # http://localhost:3000 （資料地圖）、/model.html（工具）
```

選用步驟：`npm run prep:food`（餐飲業者，需下載約 400 MB）、`npm run build:model-texture`（衛星頂面貼圖）、
`npm run fetch:spray && npm run parse:spray`（噴藥日程，需 poppler 的 `pdftotext`）、`npm run build:demo`（寧夏情境資料）。
各指令說明見 `package.json`。`dist/` 是完整靜態成品，push 到 `main` 會由 GitHub Actions 自動部署到 GitHub Pages。

## 系統架構

```
data.taipei / data.gov.tw / 內政部 DTM / Sentinel-2 / GBIF
        │  scripts/fetch*.mjs、fetch-spray.py
        ▼
      raw/                      原始檔（不入版控）
        │  scripts/build*.mjs、geocode.py、merge_food.py、parse-spray.py
        ▼
   dist/data/                   GeoJSON、JSON、二進位網格、貼圖（全部預先算好）
        │
        ├─ dist/index.html      資料地圖（deck.gl，單檔）
        └─ dist/model.html      立體模型＋管理工具（three.js，ES modules）
              ├─ scene.js        地形、貼圖、相機、拾取
              ├─ engine.js       族群模型（純函式，有測試）
              ├─ villages / card / tasks / reports / spray / settings / notify
              ├─ timeline.js     過去 90 天 → 未來 30 天
              ├─ demo.js / video.js / tour.js   示範、影片、導覽
              └─ store.js        localStorage（任務、回報、設定、稽核）
```

沒有後端：所有計算在建置階段或瀏覽器內完成，狀態存在 localStorage。這是黑客松 MVP 的刻意取捨，也是落地時第一個要換掉的地方（見〈如果上任 100 天要落地〉）。

## 資料與模型（摘要）

| 類別 | 來源（提供機關） | 在模型中的角色 |
|---|---|---|
| 污水下水道管線、人孔、陰井 | 工務局衛工處 | 因子 1；管線 99.9% 可畫出 |
| 雨水下水道人孔 | 工務局水利處 | 因子 2 |
| 攤販集中場、傳統市場 | 市場處 | 因子 3、4 |
| 餐飲業者（食藥署、財政部、衛生局三份合併） | 衛福部、財政部、衛生局 | 因子 5；同門牌 n 家取 √n |
| 垃圾車停靠點 | 環境保護局 | 因子 6 |
| 廚餘收受點、疑似廚餘暫置點 | 環保局、EcoSentinel（民間） | 對照圖層 |
| 鳳頭蒼鷹紀錄 | GBIF、iNaturalist | 投藥任務的二次中毒提示 |
| 戶外環境噴藥日程 | 環保局各區清潔隊 | 定期噴藥任務（唯讀） |
| 陳情系統類別資料（119 個月） | 研考會 | 時間序列對照 |
| 里界、門牌位置 | 民政局 | 里單位、地址定位 |
| 20 m DTM、Sentinel-2 L2A、都市計畫分區 | 內政部、Copernicus、都發局 | 立體模型 |

- 熱力：各因子以高斯核平滑、第 99 百分位正規化、等權平均、γ 1.25；參數集中在 `scripts/build.mjs` 的 `HEAT`。
- 族群模型關鍵參數：成長率 0.02/日（Bentley 1959；Byers 2019）、第二代抗凝血劑撲殺率 95%（Buckle 2012）、外溢環帶 300 m 與回報半徑 150 m（Byers 2019）、猛禽提示 1 km（Hong 2019）。其餘標示「假設」。部分文獻為轉引，簡報前應核對原文。
- 完整來源表、計算步驟、效能實測與限制：[docs/data-and-methods.md](docs/data-and-methods.md)。

## 如果上任 100 天要落地，需要做什麼

目前的成品證明了「環境因子 → 熱區 → 任務 → 預估 → 通知」這條流程在技術上可行。
要變成市府日常使用的系統，差的不是功能，而是**真實資料、校正、權責與基礎建設**。以下假設由環保局水質病媒管制科主責，以 100 天為一個週期。

### 第 0 天先決定的三件事
1. **主責單位與資料窗口**：環保局（病媒防治、清潔隊、噴藥日程）、市場處（市場與攤販集中場）、衛工處與水利處（下水道）、資訊局（帳號與主機）。沒有指定的資料窗口，後面每一步都會卡在「要資料」。
2. **第 100 天的驗收標準**：建議兩條——(a) 模型的高風險里（前 20%）在試點期間涵蓋的實際通報比例 ≥ 60%；(b) 試點區的任務從建立到民眾通知全程在系統內完成，無紙本平行作業。
3. **不做的事**：不在 100 天內做第二個主題、不做公開民眾版、不替換現有 1999 派工系統。先把鼠類這條線走通。

### 第 1–30 天：把模擬換成真實資料
| 項目 | 內容 | 交付物 |
|---|---|---|
| 真實通報資料 | 取得 1999 與病媒科受理的鼠類通報（含座標或地址、日期、跡證）；若只有地址，沿用本專案的門牌比對定位 | 近 3 年通報資料集、匯入格式對照表 |
| 防治成果資料 | 清潔隊與外包廠商的投藥點位、餌站消耗、捕獲數；這是校正模型唯一的 ground truth | 每案一列的防治紀錄格式 |
| 噴藥日程結構化 | 日程改由清潔隊以表單或 CSV 提供，不再從 PDF 月曆解析 | 日程資料規格、每月更新流程 |
| 里長與通知名單 | 民政局提供里辦公處聯絡資料（非開放資料，需公務用途授權） | 通知名單維護流程 |
| 資料盤點與分級 | 哪些資料可公開、哪些僅內部、哪些含個資 | 資料分級表 |

### 第 31–60 天：校正模型、修正流程
| 項目 | 內容 | 交付物 |
|---|---|---|
| 模型校正 | 用通報與捕獲資料做留出驗證，擬合六項因子權重、σ、回報半衰期；核對文獻原文，把「假設」逐項換成有依據的值或市府自己的數據 | 校正報告、更新後的 `params.js` |
| 增加因子 | 建物屋齡與老舊社區、餐飲廢棄物收運點、工地——現在未納入 | 因子清單與資料來源 |
| 任務流程對齊 SOP | 四種任務類型的欄位、配套措施（鼠屍清理、藥物回收）、經費欄位與現行公文流程對齊；確認外包廠商如何填報 | 任務 SOP v1、欄位變更清單 |
| 通知流程 | 民眾通知的審核與發送權責、公告稿範本法制確認、臺北通推播的串接窗口與條件 | 通知作業規範 |
| 猛禽與藥劑規範 | 第二代抗凝血劑使用條件、1 km 猛禽提示是否納入正式規範（與農業局、台灣猛禽研究會確認） | 藥劑使用指引 |

### 第 61–100 天：試點上線
| 項目 | 內容 | 交付物 |
|---|---|---|
| 基礎建設 | 加後端：伺服器端儲存、公務帳號（臺北市政府 SSO）登入、角色權限、不可修改的稽核紀錄；部署在市府機房或既有雲端；資安檢核 | 系統架構文件、資安檢核報告 |
| 試點 | 選 2–3 區（萬華、大同、中山，通報最多）跑一個完整防治週期（約 6–8 週）：熱區 → 任務 → 執行 → 回報 → 預估對照 | 試點紀錄、預估 vs 實際對照 |
| 每日資料更新 | 通報與任務每日進系統；因子資料每季重建 | 排程與監控 |
| 使用者訓練 | 病媒科承辦、清潔隊分隊長、外包廠商各一場；新手導覽與操作手冊更新為正式版 | 操作手冊、訓練紀錄 |
| 驗收與下一步 | 對照第 0 天的兩條驗收標準；決定擴大到全市與第二主題（建議登革熱病媒蚊，噴藥日程已在系統內） | 驗收報告、下一期計畫 |

### 主要風險
- **拿不到有座標的通報與防治資料**：模型無法校正，只能停留在環境推估。對策：第 0 天就簽資料提供協議；地址以門牌比對定位（本專案已有工具）。
- **模型預估與實際落差大**：第 31–60 天的校正若不理想，先把工具定位為「任務與通知的管理平台」，熱區作參考，不作決策依據。
- **跨局處分工**：市場、下水道、清潔隊分屬不同局處，任務執行單位需要明確權責。對策：由研考會或副秘書長層級召集。
- **資安與個資**：里長聯絡資料與通報人資訊屬個資，必須在後端完成權限與稽核後才能匯入，不能用目前的 localStorage 版本。

## 已知限制

- 回報與任務為模擬或示範資料；熱區與預估未用實際捕鼠或通報數校正。
- 任務、設定、稽核紀錄存在瀏覽器 localStorage，可被清除；身分只記錄不限制權限。
- 民眾通知只產生清單與公告稿，不實際發送；臺北通推播為概念示意。
- 未納入建物屋齡、工地等因子；見鼠地圖（ratdar）通報僅有上線初期資料，只作方向性對照。
- 立體模型未擠出建物：市府開放的建照資料不足以還原全市量體。
- 詳細限制與資料品質備註見 [docs/data-and-methods.md](docs/data-and-methods.md)。
